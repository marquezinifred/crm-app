Camada 01 · Negócio

O que o sistema faz

CRM B2B multi-tenant para operação comercial completa: da captação do lead ao contrato ativo, com estrutura organizacional hierárquica, aprovações, metas por unidade e uma camada de IA que assiste o vendedor. Cada tenant é um cliente isolado; os papéis definem o que cada pessoa vê e pode fazer.

Módulos por domínio

Operação comercial

O núcleo do dia a dia do vendedor.

  • Pipeline — kanban + detalhe, 7 estágios
  • Empresas & contatos — CNPJ/CEP auto-fill
  • Atividades & tarefas — timeline, escalonamento
  • Inbound — captura por form/webhook + parser IA

Documentos & fechamento

Da proposta ao contrato assinado.

  • Propostas — versões + comparação por IA
  • Aprovações — motor de regras por margem/valor
  • Contratos — handoff automático + renovação
  • Parceiros — comissões + aceite de T&C

Estrutura & metas

Hierarquia comercial e acompanhamento.

  • Estrutura comercial — árvore ltree por tenant
  • Transferência de oportunidade — fluxo via gestor
  • Metas por unidade — quotas + progresso (15H)
  • Reconcile de aprovações — órfãs reatribuídas

Inteligência (IA)

Assistência sem expor dados sensíveis.

  • Resumo de reuniões → tarefas sugeridas
  • Parser de leads inbound (regex + fallback IA)
  • Busca semântica + sugestão de taxas

Papéis (RBAC)
ADMIN tenant DIRETOR_COMERCIAL DIRETOR_OPERAÇÕES DIRETOR_FINANCEIRO GESTOR ANALISTA PARCEIRO row-level PLATFORM_OWNER cross-tenant

Os papéis são perfis padrão: o admin concede/revoga permissions individuais por usuário. Autoridade na estrutura comercial é estrutural (membership MANAGER + posição na árvore), nunca o papel sozinho.

Camada 02 · Técnica & Infraestrutura

Como uma requisição corre

Toda chamada autenticada atravessa a mesma espinha: o Clerk identifica a pessoa, o middleware resolve o tenant, o tRPC valida permissão e o Prisma injeta o tenant_id antes do Postgres — onde o RLS é a segunda linha de defesa. Trabalho assíncrono (e-mail, alertas, timeouts, reconcile) roda em workers separados.

Apêndice técnico · stack
Frontend Next.js 14
App Router + React Server Components, Tailwind + design system Venzo, PWA. Rotas intercepting para detail-sheet. Dark default sem FOUC.
API interna tRPC
Type-safe ponta a ponta. Middlewares monitor → mapErrors → enforceAuth → withPermission. API pública REST em /api/v1.
Banco PostgreSQL · Neon
Serverless com autosuspend. Prisma + RLS. Extensões ltree (hierarquia), pgvector (busca), citext, pgcrypto. 35 migrations versionadas.
Auth Clerk
Google/Microsoft OAuth, magic link, TOTP 2FA. JWT com public.tenantId/role. Webhooks sincronizam usuários.
Jobs BullMQ + Redis
Workers com cron (alertas 07:00, rollups madrugada, timeout de transferência, reconcile 03:00). Idempotentes e best-effort por tenant.
Hospedagem
Vercel (código/edge, região gru1) · Neon (banco serverless) · Railway (processo de workers) · Cloudflare (WAF/CDN).
Observabilidade
Sentry (erros) + Axiom (logs estruturados). No-op silencioso sem tokens. PII nunca sai do processo para telemetria.
Kill-switches de rollout
OPPORTUNITY_TRANSFER_ENABLED SALES_STRUCTURE_ENABLED RBAC_GRANULAR_ENABLED MULTI_AI_ENABLED APPROVAL_RECONCILE_ENABLED SALES_QUOTAS_ENABLED

Toda feature nova entra atrás de uma flag envBoolean (default OFF): deploy inerte primeiro, ativação depois, rollback = virar a flag sem redeploy.

Camada 03 · Modelo de dados

Como os dados se organizam

O Tenant é a raiz de tudo: cada tabela carrega tenant_id e toda query é filtrada por ele. A oportunidade é o hub do negócio; a estrutura comercial usa ltree para hierarquia de qualquer profundidade; e tabelas transversais (auditoria, IA, billing, LGPD) acompanham cada tenant.

Apêndice técnico · invariantes de dados

Multi-tenancy

tenant_id obrigatório em toda entidade. Injeção automática pela Prisma extension quando dentro de runWithTenant(); RLS no Postgres como defesa redundante.

Soft delete universal

Nada é apagado de verdade — deleted_at em todas as entidades. Exceção: anonimização LGPD. UNIQUE parciais (WHERE deleted_at IS NULL) permitem reconvite/recriação.

Hierarquia ltree

Unidades comerciais em árvore via coluna path. Subtree (path <@ root.path) resolve visibilidade, metas e alvos de transferência — sempre por $queryRaw no repositório.

Tabelas imutáveis

Auditoria, consentimentos e logs de conexão (Marco Civil) são WORM — RLS sem políticas de UPDATE/DELETE. Billing idempotente por stripe_event_id.

Camada 04 · Segurança

Defesa em profundidade

Isolamento entre tenants é a propriedade crítica. Uma requisição passa por seis barreiras independentes, da borda ao dado — e duas precisam falhar ao mesmo tempo para que um tenant veja dados de outro. Dados sensíveis são mascarados antes de qualquer IA, e toda ação sensível vira trilha de auditoria.

Apêndice técnico · controles

Isolamento de tenant

  • Injeção automática em todo where/data
  • Backstop P-42 bloqueia payload com tenant divergente
  • RLS Postgres como 2ª linha
  • Regra: tenantId: ctx.tenantId explícito sempre

RBAC granular

  • 67 permissions resource:action
  • Overrides individuais por usuário + cache
  • Guard anti-escalada: só delega o que você tem
  • Autoridade estrutural (ltree), não só papel

Proteção de PII & IA

  • Mascaramento tokeniza nome/e-mail/CPF/CNPJ
  • Provider nunca vê PII em texto claro
  • Chaves de IA criptografadas (AES-256-GCM)
  • Prompts/payloads não vão para telemetria

Auditoria & trilha

  • Toda mutation sensível em audit_logs
  • tenantIdOverride fora do contexto tRPC
  • Impersonação do Platform Owner registrada
  • Logs de conexão WORM (Marco Civil)

LGPD & conformidade

  • Exportação de dados (JSON) + anonimização
  • Consentimento granular (cookie banner)
  • SLA 15 dias ANPD nas solicitações
  • Políticas versionadas com aceite forçado

Borda & segredos

  • Security headers globais (HSTS/CSP/XFO)
  • Rate limit por IP, sender e tenant
  • Secrets só em env, validados por Zod
  • Dependabot + Semgrep + ZAP no CI

Princípio-guia. Cada feature nasce atrás de kill-switch (default OFF), com migration aplicada antes do código e rollback por flag. Nenhuma camada confia na anterior: o isolamento de tenant é verificado em código, no banco e no backstop — de forma independente.
